Documentation

algodtop is one binary with three parts:

  • algodtop is a terminal UI in the style of top.
  • algodtop daemon collects metrics, status and log events from each node and keeps them for as long as you choose.
  • The daemon serves a web UI from files built into the binary.

Capturing data comes first. The daemon never drops or delays a sample to serve a viewer.

Install

go install algod.top@latest            # a command named algod.top
go install algod.top/algodtop@latest   # the same program, named algodtop

Use either one. Each builds the program into $(go env GOPATH)/bin, or into $GOBIN when it is set. Go names a command after the last part of its path, which is why the names differ. These docs call it algodtop, so with the first line, type algod.top in its place. One command installs both names: go install algod.top@latest algod.top/algodtop@latest.

To try it without installing, run go run algod.top@latest. Flags pass through, as in go run algod.top@latest -d ~/.mainnet.

  • It needs Go 1.27 or later. An older go command downloads the 1.27 toolchain by itself.
  • There are no version numbers. Every commit on main is a release, and algodtop version says when it was made, such as 2026-11-04 12:35 UTC (37f0e9db), 3 days old. Run the install again to update.
  • It uses no cgo and needs nothing at run time. It runs on Linux, macOS and Windows, on amd64 and arm64.
  • Every release also has binaries for each platform on GitHub, with checksums.txt and its signature. Check a download with sha256sum -c checksums.txt --ignore-missing. algodtop remote install checks the signature itself.
  • A system service on Linux copies the binary to /usr/local/bin/algodtop, so it runs as algodtop whichever name you installed.
  • To build for a server from your laptop, leave GOBIN unset and set the target. GOOS=linux GOARCH=amd64 go install algod.top/algodtop@latest writes ~/go/bin/linux_amd64/algodtop.

Quick start

algodtop                              # find the nodes on this machine and show them live
algodtop -d ~/.mainnet                # one data directory
algodtop -u http://127.0.0.1:4001     # a REST URL; tokens from $ALGOD_TOKEN and $ALGOD_ADMIN_TOKEN
algodtop -u ssh://relay.example.com/var/lib/algorand   # a node on another host, nothing installed there

Discovery looks at running algod processes, at data directories in your home directory such as ~/.mainnet, and at /var/lib/algorand. Without a daemon, the terminal UI shows live values only. To keep history, run the daemon:

algodtop daemon --discover   # find local nodes, write them to the config file, and run
algodtop                     # now shows the daemon's data, with history

The web UI is then at http://127.0.0.1:8090. The daemon can run in a terminal or tmux, or as a service that starts at login or boot (see Running as a service).

Terminal UI

The terminal UI connects to the local daemon when one is running, and shows its history. Otherwise it polls algod itself. --live skips the daemon even when one is running.

Batch mode suits scripts and cron. algodtop -b prints the node table once. -n 5 -i 10 prints it five times, 10 seconds apart, and --json prints JSON.

To view a daemon on another machine, use algodtop -H ssh://host. It runs ssh host algodtop stdio and opens no port. -H https://host:8090 works with a read-only token in --hub-token-file or $ALGODTOP_TOKEN.

Daemon and web UI

algodtop daemon runs the collectors, the store, health checks and alerts, the API and the web UI. It listens on 127.0.0.1:8090 by default. Set web.listen in the config, or pass -l ADDR. An empty value turns the web UI off.

PageShows
FleetEvery node as a card or a table row, with its health reasons, round, peers and recent bandwidth and round time.
NodeLive values with their change from 24 h ago, and synchronized charts in sections. An event lane marks restarts, config changes and alerts.
PeersCurrent connections, the history of each remote address, and inbound peers that disconnected together.
EventsA timeline and a filterable table of events, annotations and silences. You can add annotations and silences here.
CompareTwo time ranges of one node aligned at their start, or two nodes over one range, with mean, p50, p99 and the difference.
ExplorerAny stored metric with a label filter, for questions no chart anticipated.
SettingsNodes, retention and access. Editing nodes and retention here needs web.allow_config_edits.

A listener on loopback needs no password. Any other address needs one:

algodtop passwd              # the full password
algodtop passwd --read-only  # a password that can only look
algodtop passwd --token      # a read-only bearer token for scripts and -H https://

For HTTPS, set web.tls to "self-signed", or set web.tls_cert and web.tls_key.

algodtop reload and SIGHUP reload the nodes, alerts and retention. A change of listen address needs a restart. The daemon runs at a low CPU and I/O priority. In a ten-minute test with five nodes, it used about half a percent of one core, 53 MB of memory and 8 KB/s of disk writes.

Configuration

The config is one JSON file. It holds tokens and the password hash, so keep it mode 0600.

PlatformDefault path
Linux, macOS~/.config/algodtop/config.json (or $XDG_CONFIG_HOME/algodtop on Linux)
Windows%APPDATA%\algodtop\config.json
Linux system service/etc/algodtop/config.json

-c PATH or $ALGODTOP_CONFIG picks another file. This one watches two Mainnet nodes, a Testnet node and a local network, and alerts a phone through ntfy:

{
  "nodes": [
    {"name": "mainnet-1", "datadir": "~/.mainnet", "accounts": ["<your account address>"]},
    {"name": "mainnet-relay", "url": "ssh://relay.example.com/var/lib/algorand"},
    {"name": "testnet", "datadir": "~/.testnet"},
    {"name": "localnet", "url": "http://127.0.0.1:4001", "token_file": "~/localnet/algod.token"}
  ],
  "retention": {"raw": "30d", "1m": "1y", "10m": "5y", "1h": "forever"},
  "alerts": [
    {"name": "down", "expr": "down or stalled", "for": "1m", "channels": ["phone"]},
    {"name": "keys", "expr": "rule:key_expiry_warn", "channels": ["phone"]}
  ],
  "channels": {"phone": {"type": "webhook", "url": "https://ntfy.sh/your-topic"}}
}
Node fieldMeaning
nameThe name shown everywhere. Data is stored under it.
datadirA local algod data directory. algodtop reads the address and tokens from it, and follows a port change after a restart.
urlAn http:// or https:// REST URL, or ssh://host/<datadir>. Set exactly one of datadir and url.
token_file, admin_token_fileTokens for a REST URL. token and admin_token hold them inline.
accountsAccounts to watch: online status, incentive eligibility, votes and key expiry.
scrape_interval, peers_intervalOverride the defaults of 10 s for metrics and 30 s for peers.
backfill_logsRead the existing node.log and archive on first start.
disabledKeep the node in the file without watching it.

algodtop check validates the file, reaches each node, and projects the disk the store will use.

Nodes on other hosts

algodtop reaches other hosts through the system ssh, so ~/.ssh/config aliases, ProxyJump and ssh-agent all work. It always uses BatchMode=yes, so run ssh host once to accept a new host key. There are three ways to watch a node elsewhere.

A REST URL

"url": "https://host:8080" with a token. It gives status, metrics and peers, but no process stats or node.log.

SSH with nothing installed

"url": "ssh://[user@]host[:port]/var/lib/algorand". A path that starts with /~/ is in the remote home directory. algodtop reads the data directory files over SSH and reaches algod's REST port through ssh -W. The host needs cat and a POSIX shell, so it must run Linux or macOS. There are no process stats or log events, and data has gaps while the hub is offline.

An agent on the host

An agent is the daemon without rollups or a web UI. It collects on the host, including process stats and node.log, and buffers 7 days. The hub pulls from it over SSH, so the hub catches up after an outage with no gap. Alerts for an agent's nodes run on the agent. The hub adds one alert of its own: "agent unreachable".

  1. Copy algodtop to the host (see Install for a cross-build).
  2. On the host, install the agent as a service. If algod runs as its own account, as package installs do, run sudo ./algodtop service install --system --agent. If algod runs as you, run ./algodtop service install --agent.
  3. On the hub, run algodtop remote add host, then algodtop reload.

remote add checks that the agent answers before it saves anything. The hub names agent nodes <remote>/<node>. If the hub already watched that host over SSH, remote add offers to replace that node. The agent's node then takes over its name and history. algodtop remote upgrade, sync and remove cover the rest. algodtop remote install host copies a signed release and installs a user-level agent in one step, once a signed release exists for your version.

Running as a service

algodtop service explains the service for the machine it runs on, and prints the file it would write. algodtop service install writes that file, enables it and starts it. uninstall and status cover the rest. Every service restarts the daemon after a failure and runs it at a low priority. Add --agent for the agent instead of the daemon.

PlatformService
macOSA launchd user agent, ~/Library/LaunchAgents/top.algod.daemon.plist. It starts at login and logs to ~/Library/Logs/algodtop.log.
Linux, algod runs as youA systemd user unit, ~/.config/systemd/user/algodtop.service. It starts at login, or at boot after sudo loginctl enable-linger $USER. Logs: journalctl --user -u algodtop.
Linux, algod runs as another accountA system service like algorand.service, from sudo algodtop service install --system. See below.
Windowsalgodtop service prints the sc.exe commands. It does not install a Windows service yet.

A package install runs algod as the algorand account from /var/lib/algorand. The system service does the same: it runs as the owner of the data directory, from boot.

  • It reads /etc/algodtop/config.json, written from discovery when the file does not exist, and keeps its data in /var/lib/algodtop.
  • It copies the binary to /usr/local/bin/algodtop, so running the install again with a new binary is the upgrade.
  • It creates an algodtop group that may use the service's socket, and adds the person running the install to it. Members can use the terminal UI without sudo after they log in again.

Running algodtop daemon in a terminal or tmux needs no service. The install refuses while such a daemon uses the same store.

Health

Each node is OK, Warn or Critical, and lists its reasons in words, such as "participation key for ABC... expires in 6 days".

Critical

  • algod is down, or /health fails.
  • The last round is older than 30 s and the node is not in catchup.
  • The disk has less than 5% free.
  • An account's active participation key expires within 2 days. A renewed account's old key does not count.
  • A watched account was online and is now offline or suspended.
  • A watched online account's installed key is not the vote key registered on chain.
  • A watched online account has not voted for over 10 times its expected interval, which comes from its share of online stake.
  • The clock is more than 1 s off.

Warn

  • Catchup is running.
  • An account's active key expires within 14 days.
  • A watched account lost incentive eligibility.
  • The disk will fill within 14 days.
  • The node has no outgoing peers.
  • The error log rate is above its baseline.
  • The node runs an older release than another node on the same network and release channel. Developer builds take no part.
  • algodtop itself missed scrapes, dropped series, paused writes or deleted data at the disk floor.

Alerts and silences

An alert rule has a name, an expression and the channels to notify. It fires once the expression has been true for for, and clears once it has been false for cooldown, so it does not flap. A firing alert repeats every repeat, 1 h by default. Every change is stored as an event.

FieldMeaning
name, exprThe rule's name and expression.
for, cooldown, repeatDurations such as 1m or 2h. cooldown defaults to the longer of for and 1 minute, and repeat to 1 h.
severityThe severity sent with the alert.
channelsChannel names from channels.
nodesLimit the rule to these nodes. Empty means every node.

Expressions are fixed functions, not a query language:

  • A comparison, such as lag > 30s, peers_out < 1, disk_free_pct < 10% or rss > 8gib.
  • A state: down, stalled, catchup or agent_unreachable, joined with or.
  • health >= warn, or any health rule by name, such as rule:key_expiry, rule:no_votes or rule:clock.

Comparisons take lag, round_time, round_p99, cpu, rss, disk_free_pct, disk_days, peers, peers_out, peers_in, pool, tpb, error_rate, clock_offset, key_days, net_in and net_out.

Channels

"channels": {
  "phone": {"type": "webhook", "url": "https://ntfy.sh/your-topic", "template": "{{.Node}}: {{.Message}}"},
  "mail": {"type": "smtp", "smtp": {"addr": "smtp.example.com:587", "from": "algodtop@example.com",
           "to": ["ops@example.com"], "username": "algodtop", "password_file": "~/.config/algodtop/smtp.pw"}},
  "desktop": {"type": "command", "command": ["/usr/local/bin/notify-alert"]}
}

A webhook POSTs the alert as JSON, or as the output of its Go template, with any headers. A command gets the same JSON on stdin:

{"alert": "down", "node": "mainnet-1", "state": "firing", "severity": "critical",
 "message": "algod is down: connection refused", "since": 1793745203000000000,
 "time": 1793745263000000000, "host": "algod-host", "expr": "down or stalled"}

state is firing, repeat or cleared. Channels exist only in the config file. Neither UI nor the API can create or change one, because a command channel runs a program.

If the daemon or its machine dies, it can't send an alert. Set "heartbeat": {"url": "...", "interval": "1m"} to ping a healthchecks-style service, which alerts when the pings stop.

Silences

A silence stops notifications for chosen nodes and rules for a while. Health and events are still recorded.

algodtop silence --node mainnet-1 --for 15m "upgrade to 5.0.5"
algodtop silence list
algodtop silence rm ID

The terminal UI (s) and the web UI's Events page add silences too.

Storage

The daemon keeps its data in its own store, with no database to run.

PlatformStore
macOS~/Library/Application Support/algodtop
Linux~/.local/share/algodtop, or $XDG_DATA_HOME/algodtop
Windows%LOCALAPPDATA%\algodtop
Linux system service/var/lib/algodtop

store_dir in the config moves it. Data passes through four tiers, each kept for its own window:

TierResolutionKept by default
rawEvery sample30 days
1m1 minute1 year
10m10 minutes5 years
1h1 hourForever

With the defaults, one node settles at about 70 MB, plus under 1 MB a year for the hourly tier. algodtop check projects the size for your config. Peer sessions keep full addresses for a year (retention.peer_addresses), then only /24 totals. Warning and error log lines are kept 90 days.

When the disk falls to 5% free (disk.floor_percent), the daemon deletes the oldest data first and records it as an event. Set disk.at_floor to pause to stop writing instead.

algodtop export --node mainnet-1 --metric algodtop_round_time_seconds --from -24h > rounds.csv
algodtop export --node mainnet-1 --metric algod_network_p2p_received_bytes_total --fn rate --format json
algodtop export --events --node mainnet-1

Security

  • algodtop only reads. Its algod client sends GET requests to a fixed allowlist of paths, and sends the admin token only to the admin paths it needs.
  • algod tokens never reach a browser or the terminal UI.
  • The local socket is mode 0600, or 0660 for the algodtop group of a system service. Anyone who can open it can already read the algod tokens.
  • The web UI binds to localhost. Another address needs a password, and every request that changes state needs a CSRF token.
  • Alert channels live only in the config file, so no user of the UI can make the daemon run a program.
  • SSH runs with BatchMode=yes, so it never accepts an unknown host key or asks for a password.
